# Узкие места и замеры

Замеры сделаны на ноутбуке (Docker Desktop, WSL2): PostgreSQL 17, шаблон `bookstore_template` — 9,4 МБ.

## Что стоит одна сессия

| Ресурс | На сессию | Как мерили |
|---|---|---|
| Создание копии базы | 40–60 мс в одиночку, до ~200 мс при 10 одновременных | `\timing` в psql, поле `sandbox_ms` в `/api/sessions` |
| От открытия WebSocket до приглашения `bookstore=>` | ~160 мс в одиночку, до ~480 мс при 10 одновременных | 12 WebSocket'ов одновременно из браузера, `performance.now()` |
| Процессы | 1 psql в worker'е + 1 backend PostgreSQL | `ps`, `pg_stat_activity` |
| Память | ~2–3 МБ в PostgreSQL (backend) + ~2 МБ в worker'е (psql) | `docker stats` при 0 и 10 сессиях: PostgreSQL 181 → 205 МБ, worker 25 → 44 МБ |
| Диск | ~9,4 МБ — полная копия шаблона | `pg_database_size` |
| Подключения к Redis | ~3 | `INFO clients`: 34 клиента при 10 сессиях |

## Узкие места — от самого раннего к позднему

### 1. Подключения к PostgreSQL — первый потолок

Каждая сессия — минимум один backend, а роль может открыть до трёх подключений
(`CONNECTION LIMIT 3`). При `max_connections = 100` (по умолчанию) сервер упрётся
в лимит уже на 30–90 сессиях. PgBouncer здесь не спасёт: у каждой сессии своя роль и своя
база, переиспользовать подключения не получится. Поднимать `max_connections` можно, но каждый
backend — это отдельный процесс с собственной памятью.

**Что сделано:** лимит `MAX_SESSIONS` на worker (10) — лишние сессии получают понятный отказ,
а не ошибку подключения из psql.
**Куда расти:** несколько серверов PostgreSQL и распределение сессий между ними.

### 2. Создание копии базы

`CREATE DATABASE … TEMPLATE` по умолчанию (PostgreSQL 15+) использует стратегию `WAL_LOG`:
копирует базу поблочно с записью в WAL. Время растёт с размером шаблона и с числом
одновременных копирований.

| Стратегия | Шаблон 9,4 МБ | Замечание |
|---|---|---|
| `WAL_LOG` (по умолчанию) | 40–60 мс | линейно от размера шаблона, нагружает WAL |
| `FILE_COPY` | 100–480 мс | две контрольные точки на каждое копирование — для маленькой базы хуже |

Пул административных подключений worker'а — 4, поэтому одновременно создаются не больше
четырёх копий, остальные ждут: отсюда рост задержки при наплыве.

**Куда расти:** держать несколько готовых копий заранее (warm pool) и выдавать их мгновенно,
а новые досоздавать в фоне. Для шаблона в гигабайты — `FILE_COPY` или копии на уровне файловой
системы (снимки ZFS / btrfs).

### 3. Нет обратного давления на вывод

Worker читает pty так быстро, как psql пишет, и кладёт вывод в Redis Stream с
`MAXLEN ~ 2000`. Если браузер не успевает читать (медленная сеть) или вывод огромный, старые
записи обрезаются, и gateway молча пропустит их: `XREAD` продолжит с первой сохранившейся.

На практике это смягчает пейджер: `less -F` останавливает вывод длиннее экрана. Но
`\pset pager off` + `select * from generate_series(1, 1000000)` зальёт поток целиком.

**Куда расти:** останавливать чтение pty (`remove_reader`), пока поток длиннее порога, —
тогда psql упрётся в заполненный буфер pty и подождёт.

### 4. Подключения к Redis

Блокирующий `XREAD BLOCK` держит подключение, пока ждёт. Сейчас на каждую сессию их два
(gateway читает вывод, worker — ввод) плюс короткие запросы. Redis по умолчанию принимает
10 000 клиентов — это примерно 3 000 сессий, задолго после потолка PostgreSQL.

**Куда расти:** один `XREAD` на много потоков сразу — команда принимает список ключей,
так что один процесс может ждать ввода всех своих сессий одним подключением.

### 5. Не узкие места

- **Один event loop в worker'е.** Работа — ввод-вывод: чтение pty, `XADD`, `XREAD`. Вывод
  отправляется в Redis пачками (всё, что накопилось в очереди, — одним `XADD`).
- **Gateway** не хранит состояния: его можно масштабировать сколько угодно за балансировщиком
  (нужна поддержка WebSocket).
- **Worker'ы** масштабируются через consumer group: `docker compose up --scale worker=3`.
